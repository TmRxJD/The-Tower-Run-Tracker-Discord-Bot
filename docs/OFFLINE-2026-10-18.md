# TrackerBot local-first repair - 2026-10-18

This supersedes the October 17 investigation's decision to require fresh history on every ordinary action. Josh clarified that normal steps previously felt roughly 1-2 seconds and that basic operation must continue while the backend is unavailable.

## Confirmed causes

- Commit 9712b54 (2026-10-02 02:49 UTC) introduced complete-history preparation into review/submission/share to repair cold-cache numbering and duplicates. That correctness guard became a prerequisite to reaching the durable local write/queue path.
- October 2's durable-acknowledgement/provenance work remains present. October 6's bounded history retry preserves a failed draft for retry; it is not an offline acceptance path. Returning a retryable draft still leaves the basic ingestion blocked by cloud access.
- Command entry also required live identity resolution and returned a link-account notice on lookup failure. Settings and profile reads repeated cloud work before review/save/presentation. A 60-second identity freshness policy made already linked callers depend on backend availability.
- Logs show identity failures and a background pass aborted after five cloud failures at 2026-10-16 19:35:57 UTC. This establishes an observed outage symptom, not the date or root cause of Josh's recalled incident.
- The normal RxDB cache is memory-backed. A durable pending upload must be visible from its queue after restart even before the backend recovers.

## Repair contract

Ordinary report parsing, duplicate review, submission and sharing read local saved state. The mutation lock and owner/session/version/write-intent guards remain. New submissions commit the durable queue and captured upload target before success can be acknowledged; failed persistence rejects acceptance. Screenshot bytes still need to be downloaded/stored before their durable attachment intent is accepted.

Cloud-enabled results identify local acceptance and pending sync. They suppress unverified cloud counts/deltas and label local share copies, menu data and expanded snapshots accordingly. Cloud-sync-disabled users retain their authoritative local counts/comparisons. An optional Verify & Share success control retains the original fresh-history path, including website edit/deletion verification, without gating ordinary local use. The existing registered tracker_share prefix handles its centralized tracker_share_verified id.

Local profile choices/defaults are cached durably after successful profile reads; explicit unavailable Alt choices never silently become Main. Without cached choices, review shows Main explicitly and requires confirmation even when automatic confirmation is disabled. Expired stored identity mappings are used only as local display hints; cloud writes still require the current validated owner mapping.

New cloud-enabled deferred intents carry an automatic-recovery flag and, when applicable, a pending duplicate-check flag. Recovery reads fresh main identity fields only, coalesced within one replay pass and discarded afterward. It persists the selected existing/new cloud id before either cloud document write, preventing a failed pair write from choosing a different id on retry. Existing backoff remains; only future flagged intents continue automatic recovery beyond the legacy retry cap. Future pending users remain eligible outside the normal activity window.

Local history overlays those future durable intents onto the memory cache. It checks deletion tombstones and never promotes historical unknown-target payloads into replay. This makes a newly accepted pending report reviewable/shareable after a process restart during an outage. Unknown legacy targets remain excluded without modifying their payloads or retry metadata.

Appwrite GET calls now have a five-second caller deadline, a thirty-second outage circuit and a cap of sixteen unresolved SDK reads. Timed-out SDK reads remain tracked until they settle; later caller retries cannot amplify them without bound. This layer never times out or blindly retries uncertain writes. The durable stable queue identity handles write recovery.
