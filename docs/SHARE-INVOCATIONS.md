# Invocation-prepared Share history

## Why Share repeated the work

Commit 9712b5494413641dec1069aac72e5b4db5c50125 (October 1, “Fix cold-cache run numbering and duplicate submission checks”) replaced Share's `getLastRun(...cloudSyncMode: 'none')`/single-run cache path with `prepareBotRunUploadHistory` inside the per-user lock. The local cache could be cold, incomplete or changed; trusting its old counts could misnumber a run or miss duplicate/deleted selections. October 2 additionally refreshed the selected metrics and captured immutable public versions. Those correctness protections were intentional.

The later submission pipeline already captures complete `allRunsArr` after its verified read and durable save, then uses that array for the result's comparisons/chart and automatic log-channel sharing. But `setShareableRun` retained only the selected run, counts and screenshot. Its user-keyed UI cache has a sliding 30-minute lifetime, with no message/profile binding. The unresolved-read map in `run-upload-history` is removed on settlement. Consequently a normal Share click reread full history and extended data even immediately after a successful result. Faster paging reduced that repeated work but did not remove it.

## Current lifecycle

- Submission retains its existing fresh validation, duplicate checks, save admission and durable acknowledgement. The complete post-save history and selected run are captured coherently before releasing the mutation lock. No write check is replaced by an old invocation observation.
- Menu invocation prepares complete read-only history before enabling its prepared Share control. Complete paging, ownership/profile/schema/count validation, deadlines and fallback classification remain in the existing loader. The prepared summary uses that same full observation; a recent/partial menu prime cannot masquerade as full history.
- Prepared buttons carry a random token through the central custom-ID contract. The server entry binds owner, source message, mode, active upload-profile context and selected run. Message binding is established before the button is published. Legacy unprepared buttons retain their existing fresh-read path; missing/expired prepared tokens never fall through to a different user's or newer selected run.
- A valid prepared click reuses the entire captured history with no new cloud-history request. Current tracker disclosure settings and effective shared display settings still follow their existing checks. Counts, comparison mode and chart are computed from the complete captured array with the current allowed display flags. A footer identifies when history was captured; these are invocation snapshots, not a claim that unseen subsequent website changes are already present.
- A checkpoint validates current local membership/content, tombstones, unrepresented pending intents and the local cloud preference before using the snapshot and again immediately before public dispatch. A changed profile/mode, expired entry or incompatible observation fails closed with a private instruction to open Tracker again. New local edits/deletions and observed remote changes invalidate reuse.
- Filling an empty/partial local mirror with rows already in the captured verified observation is permitted, including partial hydration. New identities/content absent from both the prior local checkpoint and captured history are rejected; prior local rows cannot disappear silently. A newly observed version contradicting the captured content invalidates it even if its values resemble an older mirror. Transport revision fields and ID acknowledgements do not falsely invalidate data matching the capture. Dates used as chart fallbacks remain significant. Retiring an already represented upsert intent does not invalidate unchanged data; unknown historical target entries remain untouched.
- A known send failure leaves the prepared input available for retry until its original deadline. Repeated clicks do not renew that deadline. A process restart loses unpublished invocation tokens; the old token instructs the owner to prepare a new invocation. Already published immutable versions remain durable, retaining their capture time, counts, comparison and original chart for Expand after restart.

## Limits and freshness

Absolute lifetime is five minutes. There are at most 64 entries, 16 MiB per complete entry and 32 MiB total, including checkpoints. Full observations are serialized into owned UTF-8 buffers, with fresh decoded copies for consumers. Expired/evicted observations are removed as complete entries. An observation that cannot fit is never truncated; its control uses the existing fresh-read fallback.

An invocation capture cannot observe an arbitrary later website edit/deletion without another remote revision contract. Such unseen changes are not represented as live data: the public Share and Expand retain the explicit history-capture time. Local mutations and background-observed remote changes are checked. Starting a fresh invocation obtains a fresh verified observation. Current disclosure/permission checks are not cached away, and Discord still enforces channel delivery permissions. A warm click can still pay settings, acknowledgement, snapshot persistence and Discord delivery costs; zero history requests is not a zero-network or zero-latency guarantee.

The read-only snapshot's data view and the independently rebuilt RxDB cache remain distinct. The unrelated account previously reporting six cloud versus 41 cached IDs is not repaired or reconstructed by this change. Its deletion guard and historical queues are not weakened. Existing durable copies and forensic evidence are preserved separately; no claim of unique data loss or complete retention follows solely from those counts.

## Verification

Offline fixtures exercise the actual paste/review/submit pipeline, extract the generated button, and invoke the real Share handler. A 1,361-row result retains full counts and extended fields with zero additional history requests; menu-generated controls also reuse their preparation. Tests cover owner/message/profile/mode isolation, absolute expiry, mutation recheck before dispatch, cold/partial hydration, current disclosure changes, cloud preference, represented queue acknowledgements, repeated sends, known send failure recovery, restart invalidation, byte/capacity boundaries and immutable Expand capture/chart behavior. Existing legacy fresh-read tests still check website edits/deletions, partial pagination, ownership/profile mismatch, duplicate/repeated submissions, durability and offline fallback.

The controlled generated-button benchmark uses an isolated SDK adapter with 300 ms added per fresh request and mocked Discord/settings. It records actual handler duration and request counts in `temp/prepared-flow-benchmark.json`. It is separate from the read-only live backend benchmark and any natural Discord traffic. Full TypeScript, full source lint, compilation, the complete Vitest suite and all deployment guard tests must pass for the final source.

Final isolated validation: 107 files / 702 tests passed in 189.59 seconds, all 14 deployment-guard tests passed, and full types, source lint and compilation passed. The final actual-handler fixture measured prepared Share 18.7 ms / zero history requests versus fresh Share 1,476.5 ms / nine simulated SDK requests. A separate compiled-code smoke check verifies rejection of oversized entries, global-byte eviction and complete retention of the newest accepted observation. These controlled results do not establish live Discord delivery latency.

Publication remains Git push, runner pull of that exact main revision, and guarded runner-controlled activation. Require matching source/build receipts, a new PID, fresh PID-bound Discord readiness, stable restart count and unchanged protected historical queue fingerprint. Never use manual deployment fallback or synthetic Discord posts for validation.
