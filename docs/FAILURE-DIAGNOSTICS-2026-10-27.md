## Correlation, stages and privacy

Nonsecret configuration review resolves OCR to `https://api.groq.com/openai/v1/chat/completions`, with Bearer authentication and a configured-key presence flag. The configuration file predates the running process. This matches the [official endpoint](https://console.groq.com/docs/api-reference). Groq classifies [401 as authentication rejection](https://console.groq.com/docs/errors), separately from 403 permission restrictions, 404 URL/resource errors and 5xx service failures. The client records the actual response status. No credential-bearing request or validity probe was made; the old status-only record cannot distinguish an invalid/revoked credential from other account-side authentication conditions. Restoring rejected cloud access requires owner verification of the configured Groq credential/account. There is no evidence supporting an endpoint rewrite or authentication retry loop.

Interaction start/finish, submission, OCR, history/save/presentation and error records share an opaque operation UUID and PID where they execute in the same async context. A process-salted HMAC of a session key links later review/submission activity without recording its token or owner. Prepared snapshots retain only the originating operation UUID as additional diagnostic metadata, allowing a valid Share to refer to its invocation. No new persistent run field is introduced.

Existing closed operation labels now cover the source-defined error call sites. Safe exception evidence includes at most three cause objects, six existing local source locations, allowlisted exception/code/status, error shape, stack availability and a separately captured catch site. Paste wrappers preserve the original cause. Validation diagnostics contain only the fixed validator name and required-field types/presence, never values or invented validity conclusions. Stage tracking records validation, history, save and presentation settings/comparison/render/chart/bind/reply/auto-share/diagnostic/notice boundaries. Write-admission and saved flags remain distinct.

No raw report, OCR text, image, attachment filename/URL, user/profile/message ID, custom ID, token, arbitrary exception message or secret enters the new diagnostics. Existing raw logs on these targeted OCR/review/menu/router paths are replaced by safe metadata. Diagnostic alert content remains incident/category only; no new user-visible explanatory text is added and the removed capture footer stays removed.

Share completion records now include a closed `noSendReason`; prepared-control decisions separately identify missing/expired entries, binding mismatches, changed checkpoints, replacement, or checkpoint errors. They record a bounded cache age and origin operation only when the caller owns the entry. A missing entry does not claim whether a prior prune, eviction or restart removed it. Owner/message/profile/mode checks, absolute expiry, content invalidation, repeated-click and error-recovery behavior remain unchanged; no fresh history fallback is added for rejected prepared controls.

## Bounds and delivery behavior

A request still pending after five seconds emits one redacted slow record but retains its slot until settlement; it is never retried or replayed. No run-data queue is drained or modified.
