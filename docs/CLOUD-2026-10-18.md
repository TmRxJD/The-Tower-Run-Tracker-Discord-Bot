# TrackerBot cloud quantities and read-fan-out correction - 2026-10-18

The 00:45 deployment incorrectly made cloud-enabled callers use local-only views by default. It then discarded their count maps and comparisons and offered an extra verification button. This was a regression, not an acceptable interpretation of the offline requirement. Normal online functionality is restored automatically; durable local acceptance remains available when cloud is disabled or unavailable/slow.

## Corrected behavior

- Standard report review/submission/share automatically attempt cloud history when the user's cloud preference is enabled. Complete schema/ownership/pagination/count checks remain. The merged view reflects current website edits/deletions and known pending operations, without rewriting every local historical record on the foreground read.
- On a failed/slow read, the operation falls back to durable saved history and pending intents. Its displayed quantity is useful and explicitly marked locally saved rather than represented as a current cloud total. Incomplete fallback history does not produce a misleading comparison. Explicit cloud-disabled users use their local data and do not trigger run-history/identity/profile refresh reads.
- Successful full observations persist a materialized fallback history in SQLite. It survives cache-cold process restart. Partial/main-only reads cannot overwrite that complete snapshot. A fresh online operation still refreshes cloud data; a completed snapshot is not silently treated as current across website changes.
- Counts include a newly accepted submission even when the initial verified view was read-only. Pending uploads that match an existing website report count once, including legacy empty/null Main profile representations. Durable pending deletes are subtracted once. These are read-view corrections; protected historical payloads are not modified or replayed.
- Normal quantities and configured comparisons return on standard Share and submission results. The extra Verify & Share control is removed; old posted IDs remain compatible. Captured comparison data and freshness are part of immutable share snapshot versions so expansion preserves the comparison originally displayed.
- Normal parallel reads queue for one of sixteen slots instead of failing immediately. Capacity waits are bounded to fifteen seconds, active reads retain a separate five-second deadline, and queued/caller cancellation is supported. Unsettled SDK reads remain tracked after caller timeout/cancellation. The finite queue and circuit prevent amplification without treating normal capacity as network failure; uncertain writes are not timed out/replayed by this layer.

The correction retains durable queue commits before success, captured targets, stable cloud write identities, future-intent recovery/backoff and the historical owner-decision boundaries. No backend/schema/index/credential/security changes, manual real-queue replay, production network interruption, synthetic public posts or ToolsBot changes were made.
